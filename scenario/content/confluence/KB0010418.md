# KB0010418: Diagnosing idle-in-transaction sessions on PostgreSQL

Space: DBA · Owner: Database Engineering · Last updated 17 Jun 2026 by Elena Rossi

Use this when a PostgreSQL instance is at or near `max_connections`, or an application reports it cannot get a connection, and you need to know whether the database or the application is holding the connections.

## Look at what the sessions are doing

Connect on a superuser slot (the reserved slots still work when application roles are refused) and group the client backends:

```
select usename, application_name, state, count(*), max(now() - xact_start) as oldest_xact
  from pg_stat_activity where backend_type = 'client backend' group by 1, 2, 3 order by 4 desc;
```

## What the states mean

- `active`: the backend is executing a statement now. Many long-running `active` sessions mean slow queries or lock waits; look at `wait_event_type`, `wait_event` and `query`.
- `idle`: connected, no transaction open. Normal for a pool's spare connections.
- `idle in transaction`: the application opened a transaction, ran something, and has not committed or rolled back. The backend is waiting for the client (`wait_event` is usually `ClientRead`). The database is not doing any work for these sessions. They hold their connection and any locks they took until the application finishes.

A count of `idle in transaction` that grows with the application's connection count, with short `xact_start` ages that keep renewing, means the application is holding transactions open while it does something else (a remote call, a sleep, a slow step in code). The fix is in the application, not the database.

## What not to do

- Do not raise `max_connections` to make room. More slots fill the same way and the instance gets slower.
- Killing the sessions (`pg_terminate_backend`) frees slots for seconds if the application keeps opening the same transactions, and it aborts whatever those transactions were doing. Only do it with the owning team, and tell them which pids you killed.
- `idle_in_transaction_session_timeout` is a backstop, not a fix. We set it per role only with the owning team.

## Escalate

Send the grouped output and the five oldest sessions (`order by xact_start limit 5`, with `query` and `client_addr`) to the team that owns the `application_name`. The last statement in `query` usually tells them where in the code the transaction is.
