# Step 6 decisions and data fixes

Combined ruling of three independent reviews run on 2026-10-13 after the data phase (steps 0 to 5). Each reviewer decided every open point from `docs/research/ingestion-and-retrieval.md` against `docs/requirements.md`, and reviewed what is built from a different chair: an assessment lens (how an AIOps company would score it), an engineer who will build the tool layer, and an SRE who will use the agent. Their full reviews were removed once every finding had been acted on; git history keeps them. None of them read the held-out paths, and this record contains no held-out content.

Rule for ties: where two reviewers agree, that is the ruling; where all three differ, the ruling is the cheapest option that still gives a defensible answer to a named requirement, and the reason is stated.

**Answers on the named concepts.** RAG or retrieval: agentic retrieval through structured tools plus BM25 and a source inventory in context, sized by measurement. Vector search: a reasoned "no" backed by corpus sizes, with the production path. Knowledge graph: an edge table where each edge keeps its source, alias resolution with a recorded method, and a two-hop CTE; strongest when the agent catches the CMDB owner disagreeing with PagerDuty. Code versus agent: the boundary table in research section 4 goes into the write-up.

## 2. Review of what is built

All three agree the data is above the bar. The engineer verified: `make data` is deterministic, `make lint` 0 errors, `make test` 13 passed; every one of 4,038 manifest rows resolves to a served record; every handle recomputes from served bytes; `break_only_before` reproduces every multi-line record. The SRE verified the causal chain is complete at 14:52 and the connection budget holds wherever it is shown (Hikari totals, Datadog series, the pg_stat_activity paste). No scenario label (`trap`, `sig_id`, `signal`) appears in any served file.

The assessment view is to stop investing in realism after the fixes that mislead or leak. The SRE found one problem the others did not measure that does mislead: sampling. The ruling follows the assessment lens's principle and includes the SRE's finding, because it changes what the tools would report.

## 3. Data fixes, ordered

**Before any tool is built** (they would make tools report wrong or future facts). About 2.5 h.

Rates change partway through the incident, so per-minute log counts show retries, timeouts and leak warnings falling while the incident worsens, and the reconciler as the main source of new Postgres connections. Fix in the generator and `sampling:`: one constant rate per line class for the whole window, with at most one kept anchor line per host; sample per request or cart by hashing `order` or `cartId` and keep every line of a kept request; log every Postgres connection pair (about 230 more lines, still under the ceiling); leak traces at about 1 in 400 from 14:26 so they rise with the slow share; serve the rates in `integration.yaml`. The order of items 2 to 6 is re-cut by `docs/decisions/ingestion-decisions.md`: ingestion for every source lands first as step 6a, then the tools as 6a-tools; D3 stands.
