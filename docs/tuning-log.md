## Key

**The runs.**

- _Arm A_: The baseline: the model gets the commander's message, the alerts and the chat in one go and answers once. It can't look anything up. It shows what you'd get without the agent.
- _Arm C_: The agent, Smalls. It decides what to look up, keeps notes on its theories, cites the records it read, and has its report checked. Every run except arm A's is arm C.
- _Checkpoint_: The time the investigation is run as of: 14:40 or 14:52 on the day of the incident. The agent can't see anything later.
- _Batch_: A group of runs made for one purpose. Each one is a column on the charts, in the order they ran.
- _Batch names_: The labels along the bottom of each chart. p01 to p08 are the runs testing prompt changes 1 to 8; p07-guard is the tougher test of change 7. p3 and p4 (with -sol or -luna) are not prompt changes: they are phase 2's first test and baseline, one column per model. sol-shake and sol-base are phase 1's first test and baseline. eff-low and p02-low try the model thinking less. frame and frame-db-at-time give the agent a misleading message on purpose; final is two extra runs. c3 and cli-claude are runs on Claude. armA is the baseline. e4 is the 14:40-then-14:52 test, and e5 the test with search labels off.
- _Phase_: Phase 1 and phase 2 are the two rounds of improving the prompt. build and between are runs made outside those rounds.
- _Pass_: One change to the agent's instructions, aimed at one problem, written by someone who has never seen this incident so it can't be tailored to it. A pass is kept if it helps, and undone if not. Pass 0 is the original instructions.
- _Finding_: A problem seen across several runs (F-01, F-02 and so on), which a pass tries to fix.
- _Kept, reverted_: Kept: the runs still find the right cause, the problem gets better and nothing else gets worse. Reverted: the change is undone.
- _Model (set)_: Which AI model does the work. sol is the second provider's mid-priced model, luna its cheaper one, and claude the first provider's. The investigator column shows the setting, such as openai@medium.
- _Effort_: How long the model thinks before each answer: low, medium or high.
- _Trigger kind_: The message the run started from. standard is the commander's real message. framing is a message that pushes a wrong answer, to check the agent isn't swayed. custom was typed by hand.
- _Guard runs_: The two misleading-message runs a change has to pass before it is kept.

**The agent.**

- _Notes (the board)_: The agent's running list of possible explanations, each with how sure it is and the evidence for and against.
- _Leading explanation_: The explanation the report puts first: what the agent says is causing the incident.
- _Roles_: Cause: what is actually broken. Trigger: what set it off. Contributing: what made it worse. Symptom: an effect, not the origin.
- _Handle_: The ID at the start of every record the agent can see, such as log:pay-01/ebfd5293. Reports cite these so every claim can be checked.
- _System evidence_: Evidence from logs, metrics, deploys or tickets, rather than only what people said in chat.
- _Wasted turn_: A round where the agent only updated its notes and looked nothing up. It costs time and money for nothing.
- _Nudge_: A reminder the agent gets when its notes haven't changed for three rounds: write down what you've found, or finish.
- _Report check_: Two checks before a report counts. One marks each claim as backed up, partly backed up, or not backed up by the evidence it cites. The other looks for a better explanation.
- _Tags_: Labels attached to records to make searching easier. They help find things but are never treated as evidence.
- _Carry-forward_: A 14:52 run that starts from what the 14:40 run found, and must use what changed in between.

**Scoring.**

- _Answer key_: What really happened, written when the incident data was made. Only the scorer sees it; the agent never does.
- _Scorer_: Code that marks each run against the answer key, plus a grading model that ticks a checklist for the 14:52 runs.
- _Found the cause_: The report's main explanation is the real cause, backed by system evidence.
- _Hard fail_: The report confidently blames the wrong thing. It's the worst outcome, because a commander would act on it.
- _Key facts_: The facts a good report must establish, each counted only if it's backed by a record the agent actually saw.
- _Red herrings_: The misleading theories built into the incident, such as the recent deploy or the full database. A run avoids one by ruling it out with evidence.
- _Passed overall_: The plan's checklist for a good run: a valid report, no made-up citations, the right cause with system evidence, wrong theories ruled out with evidence, the right owner, a list of what not to do, and finishing within budget.
- _Failure steps explained_: The grading model's four-point checklist of how the failure works. A report gets a point for each step it explains with evidence.
