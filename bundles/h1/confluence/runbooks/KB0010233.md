# KB0010233: Rolling back a Jenkins deploy

Space: OPS · Owner: Change Management · Last updated 12 May 2026 by Jordan Pike

This page covers rolling any service back to its previous version by re-running its Jenkins "<service>-deploy" job. You need access to the service's Jenkins folder and to ServiceNow.

## When to use this

Use this when a release is misbehaving in production and the fastest safe option is to put back the version that ran before it. If the problem is configuration rather than code, check with the service owner first. A rollback does not undo config changes made in the same release.

## Steps

1. Find the deploy you are reverting. In Jenkins, open the "<service>-deploy" job and look at the last successful build. Note the build number and the VERSION it used.
2. Work out the previous version. Check the release notes in the service repository, or the last successful prod deploy before the current one.
3. Click "Build with Parameters" on the "<service>-deploy" job.
4. Set VERSION to the previous version.
5. Set TARGET_ENV to prod. Check it twice; a wrong value deploys to the wrong place.
6. For a normal release, set CHANGE_TICKET to the original change ticket for the release you are reverting. This keeps the rollback linked to the change record.
7. Start the build and watch the console until it reports success.

### Emergency rollbacks

If the change window is closed or the service is down, deploy first and do the paperwork after. Leave CHANGE_TICKET empty, deploy the previous version, and raise an emergency change in ServiceNow within 24 hours. Reference the Jenkins build number of the rollback in the change so the two can be matched.

## Check the result

- Read the console output for the deploy job. Confirm the final health check passed and the version deployed is the one you asked for.
- Check the service's health endpoint and dashboard. Confirm error rates are back to the level from before the bad release.
- Check that every instance reports the rolled-back version, not a mix of old and new.

## Gotchas

- Database migrations do not roll back with the job. If the bad release ran a migration, the previous version may not start against the new schema. Ask the service owner before you rerun.
- Do not delete the failed build. Its console output is the record of what happened.
- Changing the job parameters on a build that is already running does not change that build.

## Who to tell

- Post in the service's incident channel that a rollback is running, with the build number and the version you are moving to.
- Tell the on-call engineer for the service and the change manager on duty.
- For an emergency rollback, the change manager creates or confirms the ServiceNow change.
